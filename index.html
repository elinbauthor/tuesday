Tuesday — Drive spike

Answers one question: can a static page on your phone sign into Google Drive, write your wardrobe there, and read it back? Nothing here touches the real app.

Setup, once

  1. Host this file on a real origin. GitHub Pages is easiest — a public repo, this file as index.html, Pages enabled. A file:// path will not work.
  2. In Google Cloud Console, create a project, then APIs & Services → Library and enable Google Drive API.
  3. OAuth consent screen → External → add yourself as a test user.
  4. Credentials → Create credentials → OAuth client ID → Web application. Under Authorised JavaScript origins add your Pages origin exactly, e.g. https://yourname.github.io — origin only, no path, no trailing slash.
  5. Copy the client ID below and run the tests, first on your laptop, then on your phone.

What each test is for

1Consent works at all on this device and browser. On iOS this is where popup blocking usually bites.
2Whether you re-consent every session. Tokens last about an hour; silent renewal is what makes daily use bearable.
3A write happens and Drive returns a file id.
4The bytes come back identical. Round-trip integrity, not just a 200 response.
5Timing at roughly the size of your thumbnails. If this is slow on mobile data, the design changes.
6Updating an existing file rather than piling up duplicates — how every save after the first will work.
7Ten separate 40 KB files, timed. This is the shape a real thumbnail sync would take, and it matters far more than test 5. Cleans up after itself.

Then the awkward one

Once all six pass in the browser, use Share → Add to Home Screen, open Tuesday from the icon, and run them again. iOS standalone mode has historically had its own problems with OAuth popups and a separate storage context. If it passes in Safari and fails from the icon, that is the finding — and it is better found now.

Scope note

This asks for drive.file only, which grants access to files this app creates and nothing else in your Drive. It cannot read your other documents.
